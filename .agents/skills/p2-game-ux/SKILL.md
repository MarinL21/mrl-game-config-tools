# P2 / AOA 游戏 UI/UX 设计规范

本技能用于输出符合 `P2` 项目组风格的 UX 方案，而不是沿用 `X2` 规范。

## 项目基线

- 项目名：`P2`
- 全名：`Age of Apes`
- 别名：`AOA`
- 游戏类型：横版 SLG
- 设计基准尺寸：`1376 x 768`
- 商店链接：[Google Play - Age of Apes](https://play.google.com/store/apps/details?id=com.tap4fun.ape.gplay)

## 何时使用

当用户提出以下需求时，优先按本 skill 输出：

- `P2/AOA` 的界面设计、交互草图、体验优化
- 活动页、运营玩法、付费弹窗、抽奖页、收集页、组队玩法
- HUD 入口、二级页、弹窗层、奖励反馈、状态流转
- 需要把策划需求整理成可评审的 UX 方案图
- 需要输出“流程示意图 / 体验流程图 / 重点说明图”这类评审板

## 职责边界

1. `p2-game-ux` 负责：
   - P2 交互图
   - 页面布局
   - 组件细则
   - 状态流转
   - 界面元素执行规范
2. `p2_document` 负责：
   - 文档结构
   - Google Sheets 章节编排
   - 文案落表
   - 分类标识
3. 只要任务进入 `界面怎么画 / 交互怎么走 / 元素怎么摆 / 挂点怎么承接` 这一层，默认以 `p2-game-ux` 为主规范，不把这部分细则散落在文档 skill 中。

## 输出原则

1. 默认以 `1376 x 768` 横版画布思考布局。
2. 优先说明入口、主界面、弹窗层、结果反馈四段结构。
3. 方案必须写清楚状态流转，而不只是静态界面。
4. 优先复用 `P2` 现有体验母版，不凭空发明一套新系统。
5. 文案、按钮、资源位、奖励展示要服务于“快理解、快决策、快领取”。
6. 若某个玩法是“主活动的一部分”，则入口必须挂在该主活动现有页面内，不得额外发明一个独立主页面或独立活动中心承载。
7. 这类子玩法的入口优先复用主活动页中已存在的资源位、礼盒位、装置位或按钮位，并保持原页面结构不被打散。
8. 只要交付物是 `活动界面 UX 图`，默认必须保留左侧页签导航条；不能把活动界面画成无页签的纯弹窗大页，除非用户明确指定该页面本身就是独立弹窗层。
9. 左侧页签导航条需要继续承担 `活动分类 / 玩法切换 / 当前选中态` 的语义，不能只做装饰。
10. 若主玩法以弹窗层承载，也必须先说明它是从哪个带左侧页签的活动页进入，再单独展示弹窗层。
11. 若用户已经提供了带左侧页签导航条的参考图，后续所有活动主界面和二级活动页默认沿用该导航条的样式语言、宽度比例、按钮造型、选中态和材质表现，不能自行改成另一套导航条皮肤。
12. 导航条允许替换页签名称与红点状态，但不允许擅自替换为不同项目风格、不同圆角逻辑、不同按钮结构或不同高亮形态。
13. 若用户已明确指定某张导航条截图作为参考母版，则该截图默认升级为当前任务的导航条唯一示例；后续所有活动主界面、二级活动页、流程图里的活动页缩略图，都必须复用这张导航条的样式语言。

26. 若活动页进入了二级玩法页，只要本质仍是活动界面而非纯结果弹窗/纯确认弹窗，默认继续保留这四个骨架元素。
27. 活动主界面默认必须增加 `规则说明` 按钮，并提供与当前玩法直接对应的规则说明文本。
28. `规则说明` 不能只是一个空按钮占位，必须能让玩家明确看到或进入查看：
   - 玩法目标
   - 核心操作方式
   - 奖励获取方式
   - 关键限制条件
29. `规则说明` 的默认交互不是常驻大段文本，而是活动界面左下角固定放一个 `❗` 按钮。
30. 玩家点击左下角 `❗` 按钮后，再进入规则说明弹窗或说明层查看完整规则。
31. 除非用户明确指定，否则不要在活动主界面常驻露出 1-2 句规则摘要文本。

## 仅换包装（换皮）时的约束

当用户明确为 **只换包装 / 换皮 / 主题皮肤 / 视觉主题**（不要求改玩法结构、不改信息架构）时，须遵守：

1. **参考截图即布局母版**：若用户提供了现有界面的参考截图（真机或效果图），则该图的 **界面框架、分区比例、控件相对位置、整体尺寸与画幅比例** 视为锁定基准。**不得**因主题更好看而擅自改成别的版式（例如：竖条导航改成顶栏、转盘缩小或移位、首充从「左角色右礼包」改成居中大卡、改掉奖励格数量或排布等）。
2. **默认保持不变的要素**（除非用户写明可以动）：左侧页签栏宽度与结构、顶栏（返回 / 标题 / 货币区）、主内容区的 **栅格与信息区划分**（如礼包页「左立绘视窗 + 右侧文案与奖励排布」、转盘页「中央轮盘 + 轮盘左侧竖条进度 + 右下操作区」）、底部倒计时与规则入口等与参考图 **一致**。
3. **仅允许替换的范围** 以用户指令为准，常见约定：
   - **首充 / 礼包类**：通常只替换 **背景 banner / 环境氛围** 与 **左侧英雄或主体展示图**；促销文案区、奖励格、折扣角标、价格按钮等的 **布局、数量与相对位置** 与参考图保持一致。
   - **转盘 / 抽奖类**：通常只替换 **转盘外观（盘心、分格皮肤、外框材质）** 与 **背景 banner**；轮盘占位大小、分格数量、左侧附属进度条、旋转按钮与价格区的 **位置与层级** 与参考图保持一致。
4. **交付物说明**：用 AI 或概念图做换皮示意时，须在答复中说明 —— **像素级对齐以工程 prefab / 原界面尺寸为准**，概念图用于肤色与氛围对齐；若需量产切图，应在 **固定模板或工程导出画布** 内由原画或 UI 制作，避免在无序生图里改框架。
5. **与本节冲突时**：若用户同时提到「换包装」和「改版布局」，以用户 **最新、最明确** 的一句为准；若未澄清，默认 **只换包装则布局与尺寸不动**，并可向用户确认是否允许动结构。

**触发词示例**：只换包装、换皮、同款布局、保持原版式、在现界面上换主题、不要改布局、参考截图上的框架不变。

## P2 视觉与信息调性

### 整体风格

- 写实卡通 + 废土猴子题材 + 军事/机械感。
- 大部分功能界面采用深色底，核心操作用高饱和亮色拉出层级。
- 活动界面常见“深灰背景 + 亮色 banner + 高对比按钮 + 多奖励格子”结构。
- 功能页强调资源价值感、成长感、累积感、限时感。

### 色彩角色

| 角色 | 建议色向 | 用途 |
| --- | --- | --- |
| 主强调 | 黄 / 橙 / 金 | 主 CTA、奖励、进度完成、价值感 |
| 次强调 | 蓝 / 青 | 次按钮、功能入口、科技/系统信息 |
| 成功 | 绿 | 可领取、强化成功、正向增长 |
| 风险 | 红 | 关闭、取消、资源不足、危险提醒 |
| 背景 | 深灰 / 黑灰 / 深蓝灰 | 主背景、遮罩、容器外框 |

### 文案语气

- 直接，不绕。
- 先结果，后说明。
- 按钮文案优先使用动作词，如“前往”“开启”“购买”“刷新”“领取”。
- 限时、折扣、保底、累计、概率等信息必须可快速扫读。

## 画布与布局基准

### 横版安全区

- 左上：返回、标题、活动分组、规则入口。
- 右上：货币、倒计时、帮助、关闭。
- 左侧：页签导航，适合 4 到 8 个一级分类。
- 中央：主玩法区，必须承担主要理解与操作。
- 底部：主按钮、阶段进度、奖励轨道、说明提示。

### 布局原则

- 主要玩法区保持居中，不把关键操作压到四角。
- 左侧页签固定语义，避免同一位置反复切换按钮性质。
- 活动界面的左侧页签导航条默认视为页面骨架的一部分，不能省略。
- 若已有参考导航条，则所有同链路页面统一复用同一套左侧导航条样式，不得页面之间自行换皮。
- 若已有指定导航条示例图，则默认先对齐该示例图，再设计中部玩法区和右侧信息区。
- 右侧适合放奖励预览、任务、补充说明、快捷购买。
- 弹窗宽度优先控制在主画布的 `40% - 70%`，避免过满。
- 大型活动主页面通常采用“左导航 + 中玩法 + 右说明/奖励”的三段式。

## 界面层级模型

### L1 入口层

- 主城 HUD 入口
- 活动 banner
- 节日入口
- 个人信息/英雄/背包挂件入口

目标：告诉玩家“这里有事可做”，不承载完整规则。

补充规则：

- 若玩法是某个活动页内的子玩法，则不新增独立 `L1` 入口，而是在该活动 `L2` 页面中通过局部入口承接。
- 子玩法从主活动页进入后，再进入独立的 `L2` 子界面或 `L3` 弹窗层。

### L2 玩法页

- 玩法主棋盘 / 主转盘 / 主养成区
- 页签切换
- 任务、奖励、商店、规则等并列模块

目标：让玩家完成一轮核心行为。

### L3 弹窗层

- 规则说明
- 奖励预览
- 确认购买
- 选择 Buff / 选择队友 / 结果揭示

目标：一次只解决一个决定。

## P2 通用组件规范

### 标题区

- 左上标题优先，和返回按钮形成稳定头部。
- 标题通常配活动名、系统名或阶段名。
- 活动页标题可叠加版本、时间、标签色条。
- 活动界面左上角默认采用 `活动名称 + 一小段活动描述` 的双层结构，描述用于快速说明玩法目标、奖励价值或行动指引，字数宜短，不写成长段说明。

### 页签

- `P2` 常用左侧竖向页签。
- 当前态要明显高亮，并且与内容区主色呼应。
- 不同页签数量很多时，保证可滚动和命名可读。

### 按钮

| 类型 | 颜色倾向 | 用途 |
| --- | --- | --- |
| 主按钮 | 黄 / 橙 / 金 | 购买、确认、领取、开始 |
| 次按钮 | 蓝 / 青 | 跳转、预览、次要确认 |
| 风险按钮 | 红 | 取消、关闭危险操作 |
| 灰态按钮 | 灰 | 未解锁、条件不足、冷却中 |

按钮规则：

- 主按钮永远只保留一个视觉主角。
- 双按钮弹窗必须保证主次清晰，不能两个都抢眼。
- 禁用态不能只变灰，最好附带原因提示入口。

### 物品格与奖励格

- 奖励格必须统一边框、底板、角标规则。
- 支持数量角标、品质色、锁定态、已领取态。
- 格子周围的高亮、描边、发光要服务于“值不值得点”。

### 进度条

`P2` 中的进度条常承担四类语义：

- 累计充值 / 累计活跃
- 收集完成度
- 强化 / 升级成长
- 阶段目标达成

统一状态：

- 未开始：灰底
- 进行中：主色填充
- 可领取：高亮闪动
- 已完成：打勾或置灰保留结果
- 已满级：显示 `MAX` 或封顶状态

### 提示与标记

- 红点：有可操作收益，不用于普通提醒。
- 倒计时：必须固定位置，避免玩家找不到。
- 折扣角标：统一斜角或角贴样式。
- 锁定态：不能只加锁，要告诉玩家解锁条件。
- 活动页右上区域默认保留 `CD/资产条`，用于承载活动货币、关键资产、快捷购买或相关资源入口。
- 活动页右下区域默认保留 `活动倒计时`，用于提示活动剩余时间或阶段结束时间，不要随意挪到说明文案内部。

## P2 交互反馈规范

### 点击反馈

- 按钮点击：轻微缩放或压暗。
- 卡片点击：描边增强、底板发光、内容轻微抬升。
- 长链路操作：进入 `loading / 处理中 / 结果` 三段反馈。

### 成功反馈

- 奖励飞入资源栏。
- 数值滚动增长。
- 稀有奖励增加金光、破框、全屏聚焦或开箱感。

### 失败反馈

- 资源不足：高亮缺少资源，并给获取入口。
- 条件不满足：明确条件，不只提示“无法操作”。
- 中断行为：保留状态或给回流入口。
- 活动页默认必须补齐异常态，包括断网、数据加载失败、排行拉取失败、倒计时异常；不能只画正常态。

### 弹窗规范

- 信息弹窗：看完可关，支持点空白关闭。
- 确认弹窗：必须双按钮，并写清消耗。
- 结果弹窗：强调结果，不重复输入信息。
- 选择弹窗：先选后确认，避免误触即提交。

## P2 高复用玩法模式库

以下模式来自当前 `P2/AOA` 参考图，应优先复用。

### 1. 英雄养成与共享强化

参考：`红色英雄系统`

适用场景：

- 英雄等级拓展
- 共鸣 / 共享升级
- 英雄碎片、天赋、能力共享

交互模板：

`入口页 -> 英雄主界面 -> 共享/升级弹窗 -> 结果确认 -> 属性回显`

关键规则：

- 左侧保留英雄切换与信息入口。
- 中央突出当前养成对象。
- 右侧呈现成长路径、消耗和战力变化。
- “共享”类系统必须说明共享对象、共享收益、解除成本。

### 2. 蛋壳/孵化/开启类活动

参考：`砸金蛋活动`

适用场景：

- 充值解锁奖池
- 累积开启宝盒
- 节日蛋壳、碎片合成、分阶段开奖

交互模板：

`活动入口 -> 充值/达成条件 -> 开启确认 -> 揭晓动画 -> 奖励陈列`

关键规则：

- “开启前”和“开启后”必须是两套视觉状态。
- 开启动作需要有短动画，避免纯瞬时切状态。
- 奖励揭晓后应紧跟去向说明，如进入背包、继续开启、领取累计奖励。

### 3. 累积储蓄/投币成长

参考：`猴猴币活动`

适用场景：

- 存钱罐
- 累计投入换回报
- 资源成长型节日装置

交互模板：

`主活动页 -> 投入资源 -> 装置成长表现 -> 达标领奖 -> 重置/下一轮`

关键规则：

- 装置本体必须承担成长可视化。
- 当前投入、下一档收益、达标条件要同时可见。
- 一轮结束后给出是否继续的明确分叉。

### 4. 组队合作活动

参考：`节日大富翁活动增加小队合作`、`节日版赛车维修组队系列活动`

适用场景：

- 联盟协作
- 小队建设
- 共建型节日玩法

交互模板：

`进入活动 -> 创建/加入队伍 -> 阶段任务推进 -> 队员贡献展示 -> 阶段领奖`

关键规则：

- 队伍状态和个人状态必须分区。
- 邀请、退出、踢出、补位都要有明确反馈。
- 协作玩法要有“我该做什么”的直达任务入口。
- 阶段推进尽量用线路、节点或大装置变化来承载。

### 5. Buff 配置与多人编队扩展

参考：`围剿变异猴 - 等级拓展`

适用场景：

- 团队增益选择
- 编队位扩展
- 历史战绩与推荐配置

交互模板：

`主玩法页 -> 编队/选择 Buff -> 预览加成 -> 确认出战 -> 战绩回看`

关键规则：

- Buff 选择窗口里要同时支持“看效果”和“看来源”。
- 编队变化必须实时刷新战力或关键指标。
- 历史记录要为下一次决策服务，而不是纯展示。

### 6. Gacha + 累计目标双层活动

参考：`2月节日活动 - 新Gacha + 累计活动`

适用场景：

- 抽格子
- 投掷式随机推进
- 抽奖和累计任务并存

交互模板：

`活动主页 -> 选择模式 -> 单次/多次抽取 -> 动画推进 -> 奖励结果 -> 累计目标回收`

关键规则：

- “抽取过程”要可理解，不能只看结果。
- 抽奖区和累计任务区要明显分层，避免互抢注意力。
- 如果有苦难/寻宝等子模式，切换成本要低。

### 7. Bingo / 棋盘返利

参考：`新节日累充活动 - Bingo返利`

适用场景：

- 连线奖励
- 累充返利
- 多宫格抽奖

交互模板：

`达成条件 -> 点亮格子 -> 连线判定 -> 奖励弹窗 -> 完成大目标`

关键规则：

- 当前已点亮格、待点亮格、大奖格状态必须一眼区分。
- 连线形成瞬间要有明显动效反馈。
- 棋盘外的任务、次数、货币不要压过棋盘主玩法。

### 8. 卡册收集与礼包联动

参考：`节日集卡册 + 相关礼包`

适用场景：

- 图鉴收集
- 卡册合成
- 收集页与礼包售卖联动

交互模板：

`入口露出 -> 卡册总览 -> 单卡详情 -> 收集奖励 -> 礼包承接`

关键规则：

- 卡册界面要先给“完成了多少”，再给单卡细节。
- 未收集、可合成、已拥有、已满星要有稳定态。
- 商业化入口应顺着收集动机出现，不要突然插入。

### 9. 砍价 / 挖矿 / 分阶段报价礼包

参考：`挖矿砍价礼包`

适用场景：

- 逐次降价礼包
- 行为积累换低价
- 矿石转化价值感玩法

交互模板：

`进入活动 -> 累积行为 -> 价格下降/奖励变化 -> 确认购买 -> 结果展示`

关键规则：

- 当前价格、原价、还能降多少必须同屏。
- 降价行为和视觉进展要绑定。
- 非购买用户也应能理解下次触发条件。

## 活动页通用结构

对于大多数 `P2` 节日或运营活动，优先使用以下骨架：

1. 左侧：活动页签或模式切换。
2. 中央：核心互动区，如棋盘、装置、队伍、奖池。
3. 右侧：任务、奖励、规则摘要、资源。
4. 顶部：标题、倒计时、货币、帮助。
5. 底部：主操作按钮、进度条、阶段奖励。

补充要求：

- 活动界面左下角默认固定保留一个 `❗` 规则按钮。
- 点击该 `❗` 按钮后，进入完整规则弹窗或说明层。
- 除非用户明确要求，否则活动主界面不常驻摆放规则摘要文本。

## 小组竞速活动 UX 硬规则

当任务对象是 `5人小组竞速 / 多轮竞速 / 倍率晋级` 时，以下 UX 项默认必须满足：

### 1. 头部竞争信息

1. 主界面不能只展示 `距第3名差值`。
2. 不同排名默认展示：
   - 第1名：`领先第2名差值`
   - 第2-3名：`距上一名差值`
   - 第4-5名：`距第3名差值`
3. 排行榜弹窗也必须同步这套差值逻辑，不能只服务保级玩家。

### 2. 规则入口

1. 主活动页和二级玩法页默认都要有 `规则说明` 入口。
2. 默认优先使用左下角 `❗` 规则按钮；若用户明确指定其他位置，再按指定调整。
3. 规则弹窗至少一屏讲清：
   - 前3晋级
   - 后2失败
   - 倍率变化
   - 单轮结算条件

### 3. 单轮时间展示

1. 只要玩法存在 `单轮`，主界面必须单独展示 `本轮倒计时`。
2. 活动总倒计时与单轮倒计时不能混成一个。
3. 默认同时展示：
   - `活动剩余时间`
   - `本轮剩余时间`

### 4. 高倍率容错可视化

1. 若方案包含 `掉段缓冲 / 首败保护 / 高倍率保护`，主界面必须可见当前保护状态。
2. 若没有保护，也要在规则弹窗和结算弹窗中明确写出 `失败后回x1`。
3. 结算弹窗必须明确表现倍率变化结果，不能只给奖励不写倍率去向。

### 5. 积分来源映射

1. 主界面上的主按钮不能只写 `前往城建`，必须配一条短说明告诉玩家去做什么能产分。
2. 默认写法：
   - `前往城建：消耗建筑加速获得积分`
   - `前往科研：消耗科研加速获得积分`
3. 若页面只保留一个主按钮，则必须在主按钮附近补一条 `产分说明`。

### 6. 排行榜信息对称

1. 排行榜展示信息必须服务当前玩法目标，优先保证玩家能快速判断竞争态势。
2. 排行榜可根据玩法需要展示：
   - 名次
   - 当前积分
   - 当前倍率
   - 与关键名次差值
3. 若展示信息较多，必须保证主次清晰，避免玩家无法快速判断自己该追谁、差多少。

### 7. 页面必备状态

1. 正常态
2. 追赶态
3. 胜利结算态
4. 失败结算态
5. 规则弹窗态
6. 异常态

### 8. 竞品参考硬规则

1. 若评审指出 `缺失竞品参考`，则后续方案里默认必须补：
   - `竞品参考界面`
   - `借鉴点`
   - `本案落地方向`
2. 竞品参考不能只写名称，至少要说明：
   - 借什么信息结构
   - 借什么竞争刺激
   - 哪些点不照搬

### 9. 竞速设计公理

1. `公理一：玩家主权不可侵犯`
   - 达标、锁位、晋级必须即时反馈。
   - UX 不得通过冻结、延迟锁位、延迟晋级提示来削弱“先到先得”。
   - 只要玩家先达标，界面上就必须立刻给出锁位或晋级结果。

2. `公理二：领先玩家的消费链路不可被等待态切断`
   - 若规则是 `先达标先晋级`，则 UX 不得把领先玩家画成进入等待态、灰态、锁定不可操作态。
   - 晋级玩家进入下一轮后，界面默认继续承接下一轮目标、下一轮消耗和下一轮竞争，不把领先玩家挂起等待。
   - 不允许为了照顾落后玩家而在界面层暗示“先晋级但需等待他人结束后再继续”。
   - 若用户明确要求 `不能有空白期`，则晋级页必须立即展示：
   - 新一轮目标
   - 新对手列表或新分组结果
   - 下一轮可继续消耗的主按钮
   - 下一轮可触发的礼包/追赶入口
   - 禁止画出“已晋级，等待队友结算”这类过渡态。

3. `公理二补充：动态分组优先承接大R链路`
   - 若玩法采用 `达标即进入下一轮`，UX 默认按 `动态分组` 承接，而不是沿用原组成员继续展示。
   - 晋级反馈后必须立即告诉玩家：
   - 已进入第几轮
   - 当前轮的新对手是谁
   - 当前轮自己的排名初始状态
   - 接下来还能通过什么方式继续拉开差距
   - 若界面上只展示“你已进入下一轮”，但没有新对手与新目标，默认判定为设计未完成。
4. `公理三：用甜头拉，不用棍子打`
   - UX 默认优先展示奖励、追赶收益、阶段回报，不主动放大惩罚。
   - `矿洞寻宝`、阶段奖励轨道、收集页默认只做正向目标承接，不做冻结惩罚表现。
   - 若规则本身存在失败惩罚，界面上也不要额外再做放大式惩罚包装。

5. `公理四：付费窗口跟随游戏节奏，不跟随时钟`
   - 付费入口默认跟随排名变化、轮次阶段、最后一席争夺等状态触发。
   - 不默认使用短时固定倒计时强弹来承接支付。
   - 若出现倒计时，仅用于说明当前争夺阶段或活动剩余时间，不作为唯一付费链路。

6. `公理五：商品价值匹配玩家时间预算`
   - 礼包优先提供与当前玩法强相关的加速、体力、资源、效率 Buff。
   - 不轻易把加速类核心价值替换成纯积分卡。
   - 若礼包服务城建/科研追分场景，界面必须让玩家看懂“买了之后能继续做什么”。

### 10. 写完后的上下文冲突复查

1. 每次写完活动页、二级页、礼包页、流程图后，必须重新检查上下文。
2. 至少核对以下内容是否冲突：
   - 页面表现 vs 核心玩法骨架
   - 活动主界面 vs 规则弹窗
   - 主界面时间展示 vs 单轮规则
   - 排行榜差值展示 vs 规则正文
   - 礼包触发场景 vs 结算条件
   - 流程图说明 vs 页面实际信息
3. 若发现存在两套口径，必须先统一，再继续出图。

### 11. 单点定义与引用优先

1. UX 页不重复定义主规则页已完整写清的规则。
2. 若某条规则已在主规则页或数值页定义，UX 页默认只写：
   - 页面怎么露出
   - 玩家在哪看到
   - 点击后进入哪里
   - 与当前页面相关的最小必要摘要
3. 禁止在 UX 页重新展开一整套倍率规则、积分换算、礼包数值配比，除非用户明确要求。
4. 若同一规则必须在 UX 页出现，优先写成引用关系，例如：
   - `失败后的倍率变化按规则2.6展示`
   - `积分来源说明引用数值sheet-三、积分参数`
5. 若同一规则在 UX 页和规则页 wording 不一致，默认以主规则页为准，并立即回收 UX 页重复描述。

## 活动二级页专项规则

### 阶段奖励与终极大奖

1. 若页面同时存在 `阶段奖励条` 与 `终极大奖`，默认优先合并成一条“看到底”的大奖轨道。
2. 终极大奖作为该轨道最右侧的最终节点，不再单独拆成并列大卡片。
3. 合并后的轨道允许占用更大横向面积，目标是玩家一眼看完：
   - 当前进度
   - 中间阶段节点
   - 终极目标
4. 轨道中的节点状态必须统一：
   - 未达成
   - 进行中
   - 可领取
   - 已领取
5. 若页面空间紧张，优先压缩边缘说明区，不压缩大奖轨道主可视面积。

### 任务关联性

1. 子玩法页中的任务语义，默认要与主活动页任务语义保持同源。
2. 如果主活动页任务是 `消耗加速进行城建 / 建筑升级 / 城建类阶段目标`，则子玩法页任务也应沿用这类表达，不改成无关任务。
3. 子玩法页任务区的作用是：
   - 告诉玩家当前这轮该做什么
   - 把主活动任务映射成竞速推进目标
   - 让玩家看懂“做主活动任务 = 推动小组竞速”
4. 禁止在子玩法页里凭空出现与主活动无关的新任务口径。
5. 若存在每日任务和阶段任务，优先先展示与主活动当前页最相关的 1-2 条任务，不堆太多条目。

## 礼包与挂点模式补充

以下规则来自近期 P2 礼包、连锁礼包、双倍券、预热活动与配套礼包示例，后续同类 UX 默认优先复用。

### 礼包参考母版原则

1. 礼包界面默认优先参考用户提供的真实 `P2` 礼包截图，不自行发明偏离项目现状的新型礼包构图。
2. 可重点参考的礼包类型包括：
   - 左侧活动导航 + 中部大礼包主视觉
   - 多档位横向/纵向礼包卡列
   - 每日限购/小额尊享包
   - 连锁礼包 / 阶段推进礼包
   - 单英雄/单养成点强价值礼包
   - 资源特权/成长特权礼包
3. 设计新的礼包页时，优先从这些参考里继承：
   - 左侧导航骨架
   - 标题与副标题位置
   - 奖励横排或礼包卡列结构
   - 价格按钮体量
   - 折扣 / ROI 贴标方式
   - 限购与剩余时间位置
4. 允许替换的是礼包主题、奖励内容、主视觉角色、活动文案和局部配色氛围；不建议替换整体信息架构。
5. 若用户未指定参考优先级，则默认先从“最接近当前礼包功能”的那张已上传礼包界面中借骨架，再做题材和包装变化。

### 礼包母版分类表

后续设计礼包界面时，默认先判断需求更接近以下哪一类，再选择对应母版：

| 母版类型 | 适用场景 | 结构特征 | 优先参考方向 |
| --- | --- | --- | --- |
| 单礼包强价值型 | 单个主推礼包、角色礼包、战力提升礼包 | 单一主视觉资产 + 横排核心奖励 + 超大价格按钮 | 强调“买了立刻变强/立刻获得”的价值感 |
| 多档位卡列型 | 新手礼包、资源礼包、经验礼包、训练礼包 | 多个礼包卡片并排陈列，每张卡独立展示奖励与价格 | 强调档位差异、可横向比较、快速决策 |
| 每日限购型 | 每日礼包、每日尊享包、小额连续购买 | 单日刷新、带每日购买限制、常见多档位并排 | 强调低门槛、高频购买、每日回访 |
| 连锁推进型 | 连锁礼包、阶段解锁礼包、再购解锁礼包 | 当前档位 + 下一档预告 + 阶段推进关系 | 强调“买完这一档后还能解锁什么” |
| 特权成长型 | 资源增产、永久特权、养成加速类礼包 | 功能型主视觉 + 权益说明 + 长效收益展示 | 强调长期收益、永久生效、系统增益 |
| 活动附属礼包型 | 挂靠主活动的资源补给包、主题配套包 | 保留活动主界面骨架，在主玩法内承接礼包售卖 | 强调与当前活动玩法/任务/资源口径强绑定 |

使用原则：

1. 若需求是“卖一个最核心的大礼包”，优先用 `单礼包强价值型`。
2. 若需求是“让玩家在多个价格档位里挑”，优先用 `多档位卡列型` 或 `每日限购型`。
3. 若需求是“买完一档继续解锁下一档”，优先用 `连锁推进型`。
4. 若需求是“售卖长期增益或永久权益”，优先用 `特权成长型`。
5. 若礼包属于活动玩法链路中的一环，而不是孤立商店页，优先用 `活动附属礼包型`，并保持活动页固定框架不丢。

### 礼包弹窗基础元素

1. 若是可购买礼包弹窗，默认至少包含：
   - 档位切换
   - ROI / 折扣 / 超值标签
   - 限购次数
   - 剩余时间
   - 主价格按钮
   - 关闭按钮
2. `切换档位` 优先放在礼包标题下方或内容区顶部，用 Tab、切签或左右切换承载。
3. `ROI标签` 优先贴在档位签、礼包角标或奖励区右上角，要求一眼可扫读，不要埋在说明文字里。
4. `限购次数` 必须和当前档位绑定显示，例如：
   - `限购1次`
   - `今日剩余1次`
   - `剩余2次`
5. 若礼包有多档位，主按钮价格和奖励内容必须随档位切换即时变化。
6. 若礼包用于承接当前风险或成长诉求，标题、副标题与奖励结构必须直接说明“买了能解决什么”。
7. 若礼包页本质属于活动体系内的礼包界面，默认也保留活动页固定框架：
   - 左侧导航条
   - 左上角活动名称和小段描述
   - 右上角 CD/资产条
   - 右下角活动倒计时

### 连锁礼包与配套礼包

1. 连锁礼包优先体现：
   - 阶段推进
   - 下一档预告
   - 已购买态
   - 关闭后扫角提示或入口保留
2. 配套礼包优先体现：
   - 与主活动行为的直接绑定
   - 主活动入口上的发光或 icon 提示
   - 弹窗内的档位切换
   - 与场景强关联的 icon / banner
3. 同类主活动下若存在多种资源口径，如建筑 / 科研 / 训练，优先共用一套礼包母版，只替换 icon、banner、标题与奖励内容。

### 任务映射规则

1. 二级玩法页中的任务，不单独发明任务体系，而是把主活动页任务映射成更适合当前玩法的推进任务。
2. 若主活动页是 `消耗加速进行城建`，则二级玩法页应优先使用：
   - `每日建筑升级`
   - `建筑加速消耗`
   - `城建积分推进`
   这类同源任务表达。
3. 任务区既要能看懂“今天做什么”，也要能看懂“做完后如何推动竞速排名”。

### 参考模式拆分

#### 1. 配套礼包入口模式

来自：`消耗活动配套礼包优化`

- 主活动页已有入口位上增加礼包 icon / 发光 / 动效
- 点击后进入礼包弹窗
- 弹窗内支持切换档位
- 礼包内容与主活动资源口径强绑定

#### 2. 单礼包强价值弹窗

来自：`启程助力`

- 单个大图资产 + 核心奖励横排
- 价格按钮极强主视觉
- 折扣 / ROI 标签外露
- 限时信息贴近奖励区或价格区

#### 3. 连锁礼包模式

来自：`美妮连锁礼包优化`、`大木直升连锁礼包`

- 当前档位、下一档、总进度一体化
- 满足条件自动弹出或扫角提示
- 关闭后保留弱提示，避免玩家丢失路径

#### 4. 主活动跳子玩法模式

来自：`皮肤投放活动新形式`、`节日挂机BP`、`KVK预热增加付费活动`

- 主活动页保留原骨架
- 通过局部入口跳转到二级玩法页
- 二级页继续承接奖励、任务、礼包
- 不单独再造一个与主活动无关的首页

## UX 方案文档写法

当需要输出交互图或设计说明时，按这个顺序组织：

1. 功能背景：一句话说明本功能解决什么问题。
2. 策划目标：增长、回流、付费、留存、协作、养成中的哪一类。
3. 入口设计：主城入口、活动入口、跳转路径。
4. 页面结构：L1/L2/L3 分层。
5. 状态流转：进入前、进行中、达成后、领奖后、失败时。
6. 特殊情况：资源不足、人数不足、背包满、次数为 0、活动过期。
7. 商业化挂点：何时弹、为何弹、是否打断。
8. 验收清单：是否能看懂、是否能做、是否愿意继续。

## 流程示意图交付模式

当用户要求输出类似“方案板 / 体验流程示意图 / 重点说明图”时，默认采用以下结构：

1. 顶部：方案标题 + 版本/用途说明。
2. 第一块：`策划需求 / 重点说明`
   - 用 1-3 个缩略图或局部示意说明改动重点。
3. 第二块：`体验流程`
   - 按 `1. 主活动页入口 -> 2. 二级玩法页 -> 3. 付费弹窗/结果层` 组织。
   - 用箭头清楚标出点击、跳转、弹出、关闭回流。
4. 若存在商业化挂点，单独补一块：
   - `礼包弹窗`
   - `购买后状态`
   - `关闭后弱提示/回流`
5. 每一块都要有简短中文标题和重点说明，不只放截图。
6. 若已有用户确认的界面图，则流程示意图优先复用这些界面图，不重新发明新的页面外观。
7. 流程示意图的最终交付尺寸可以放大，但必须是 `1376x768` 的整数倍，例如：
   - `2752x1536`
   - `4128x2304`
8. 若用户明确指定“主活动入口原图应该用我发的这张”，则入口流程图必须直接使用该原图作为主参考，不得擅自替换成旧图或二次变体。
9. 流程示意图中的每一个子画面、缩略图、示意界面，都必须保持 `P2` 横版 `16:9` 视觉比例，不允许出现任何竖版手机框、竖屏页面、细长竖卡片或竖向原型稿。
10. 若流程图中包含多个步骤页，默认优先复用已确认的横版界面图进行拼板；禁止为了“更像流程图”而把横版界面重新改画成竖版示意稿。
11. 流程示意图出图后，必须二次人工检查两层约束：
   - 整张流程板是否为横版
   - 板内每一个步骤界面是否也全部为横版
12. 只要发现任意一个步骤界面为竖版，该流程示意图即视为不合格，必须重出。

## 自查清单

### 信息与流程

- [ ] 是否在 3 步内到达核心行为
- [ ] 是否先展示目标，再展示规则
- [ ] 是否给出清晰回流路径
- [ ] 是否区分个人目标与团队目标

### 界面与组件

- [ ] 标题、页签、按钮、资源位是否位置稳定
- [ ] 是否只有一个主 CTA
- [ ] 奖励格、进度条、锁定态是否统一
- [ ] 是否存在文本过多、信息打架的问题

### 反馈与状态

- [ ] 点击后 100ms 内是否有反馈
- [ ] 成功、失败、可领取三种状态是否明确
- [ ] 是否处理资源不足、次数不足、背包满
- [ ] 结果弹窗是否让玩家知道下一步去哪

### 活动与商业化

- [ ] 是否把限时、折扣、累计收益讲清楚
- [ ] 商业化入口是否顺着动机出现
- [ ] 免费路径和付费路径是否都可理解
- [ ] 是否避免把玩家卡死在单一弹窗链路中
