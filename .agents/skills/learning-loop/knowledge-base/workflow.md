## 协作规范

### 需要用户决策时，用选择题而非开放式问题
<!-- 日期: 2026-01-30 -->

#### 场景
需要收集用户的决策、偏好、确认时（如 PRD 审查、方案选择、配置确认等）。

#### 经验
**选择题 > 开放式问题。用户选比用户想更快。**

#### 为什么
- **降低认知负担**：用户不需要从零思考，只需从选项中挑选
- **减少歧义**：每个选项含义明确，不会理解偏差
- **加速决策**：点选比打字快得多
- **避免遗漏**：选项能覆盖常见情况，提醒用户考虑周全

#### 选择题设计原则

| 原则 | 说明 |
|------|------|
| 选项互斥 | 每个选项之间不重叠 |
| 选项完整 | 覆盖主要情况，可加"其他"兜底 |
| 3-5 个选项 | 太少没选择，太多难决策 |
| 有默认推荐 | 可以有"都行，你建议"选项 |
| 有延迟选项 | 可以有"先不考虑/以后再说"选项 |

#### 适用场景
- 需求/PRD 审查时的待确认点
- 技术方案选型
- 配置项确认
- 任何需要用户做决定的地方

#### 操作方法
使用 `AskQuestion` 工具，批量收集多个决策：
```
每批 8-12 个问题
→ 收集完汇总确认
→ 直接落地到文档/代码
```

#### 反例
❌ 输出一大段分析，然后问"你怎么看？"
❌ 问"你想要什么样的？"这种开放式问题
❌ 一次只问一个问题，来回多轮

#### 正确做法
✅ 把待确认点整理成选择题
✅ 用 AskQuestion 工具批量收集
✅ 先告知总量（"大概有 20 个决策点"）
✅ 收集完后汇总成表格让用户确认

## Skill 文件存储位置区分
<!-- 日期: 2025-01-14 (更新) -->

### 场景
用户要求将信息写入某个 skill 文件时，或创建新 skill 时。

### 经验
**必须区分项目级 skill 和用户级 skill！**

| 类型 | 具体路径 | 作用范围 | 适用场景 |
|:---|:---|:---|:---|
| **用户级 skill** | `C:\Users\caoxinying\.cursor\skills\` | 全局，所有项目可用 | 通用工具、跨项目经验 |
| **项目级 skill** | `[项目目录]\.cursor\skills\` | 仅当前项目 | 项目专属资源、本地配置 |

### 关键词识别
- 用户说 **"用户 skill"** → 指 `C:\Users\caoxinying\.cursor\skills\`
- 用户说 **"项目 skill"** → 指当前项目下的 `.cursor\skills\`

### 详细说明
1. **用户级 skill** 适合：
   - `master-brain` - 调度所有项目
   - `learning-loop` - 全局学习
   - `slg-*` 系列 - 通用游戏开发经验
   - `frontend-design` - 通用前端设计

2. **项目级 skill** 适合：
   - `x2-ui-designer` - X2 项目专属 UI 规范
   - 项目特定的资源映射
   - 本地配置和约定

### 反例
❌ 用户说"创建用户 skill：master-brain"，但写到了项目目录
   - 原因：没有理解"用户 skill"的含义
   - 后果：该 skill 只在当前项目生效，无法全局使用

### 正确做法
✅ 听到"用户 skill"→ 写入 `C:\Users\caoxinying\.cursor\skills\`
✅ 听到"项目 skill"→ 写入 `[当前项目]\.cursor\skills\`
✅ 不确定时，主动询问用户

## 学习来源要全面，不能只盯着一种
<!-- 日期: 2025-01-14 -->

### 场景
设计"学习循环"功能时，只考虑了"聊天记录"这一种学习来源。

### 教训
**思考问题要全面，不能一叶障目。**

学习来源至少包括 6 大类：
1. **实时对话** - 用户的纠正、偏好、经验分享
2. **反思批评** - 用户的批评、反思、失败分析 ⭐
3. **历史内容** - 聊天记录、复盘文档、会议纪要
4. **外部知识** - 文章、规范、行业实践
5. **隐性信号** - 用户修改输出、放弃建议、多次追问
6. **总结请求** - 用户明确要求记录

### 反例
❌ 只考虑"聊天记录学习"，忽略了批评、反思、失败案例等更有价值的学习来源
❌ 用户说"思考全面一些"，说明我的方案有明显遗漏

### 正确做法
✅ 设计功能时，先列出所有可能的输入来源
✅ 用 MECE 原则检查是否有遗漏
✅ 特别关注"批评"和"失败"，这些往往是最有价值的学习来源

用户批评 - 2025-01-14

## 技术调研类问题的需求澄清方法论
<!-- 日期: 2026-01-19 -->

### 场景
用户问"某技术/产品各版本支持获取的用户数据有什么差异"，这类技术能力调研问题。

### 教训
**先问"期望的输出长什么样"，再针对性阅读文档，而不是漫无目的读完所有文档再整理。**

### 错误示范
```
用户问 → 问了4个宽泛的确认问题（版本范围、数据类型等）→ 
没有问到关键点（数据粒度：聚合统计 vs 每次请求明细）→ 
大量阅读文档（方向是"管理员数据统计"）→ 
输出详细表格 → 用户追问 → 
发现真正需求是"token明细" → 
重新定位 → 发现不支持
```

结果：多轮交互，浪费双方时间

### 正确做法
```
用户问 → 问"你期望的数据长什么样？有没有必须的字段？" → 
用户说"要 token 使用量、每次请求的模型" → 
针对性读计费模型相关文档 → 
快速确认"Copilot 不按 token 计费" → 
直接回答"不支持" + 解释原因 + 替代方案
```

结果：一轮交互解决问题

### 技术调研类问题的标准澄清流程

1. **问期望输出**
   - "你期望的数据/输出长什么样？能给个例子或模板吗？"
   - "有没有'如果没有这个就不行'的硬性要求？"

2. **识别核心约束**
   - 哪个字段/能力是必须的？
   - 如果没有这个，整个方案还有意义吗？

3. **针对性阅读**
   - 先读与核心约束相关的文档
   - 验证核心可行性

4. **快速反馈**
   - 可行 → 继续展开细节
   - 不可行 → 直接说明 + 解释原因 + 替代方案
   - 不确定 → 说明不确定，继续调研

5. **识别"产品模型差异"**
   - 用户可能用其他产品的思维模型来理解当前产品
   - 例：用 OpenAI API（按 token 计费）的思维理解 Copilot（按 Premium Requests 计费）
   - 发现这种差异时，先解释产品模型，再回答问题

### 反例
❌ 需求澄清只问"你想要什么类型的数据"这种宽泛问题
❌ 没有追问用户期望的输出形态就开始大量阅读文档
❌ 读完所有文档再整理，发现核心问题不支持

### 适用场景
- "XXX 产品/技术各版本有什么差异"
- "XXX 能不能做到 YYY"
- "调研一下 XXX 的能力边界"

## Cursor Skill 设计：如何让规则真正被执行
<!-- 日期: 2026-01-19 -->

### 场景
设计了一个 Skill 来强制执行某个流程（如"技术调研前先问用户需求"），但 AI 看到规则后仍然选择"自主优化"，没有严格遵守。

### 核心问题
**AI 会"自主判断"规则是否需要遵守，建议性语言会被忽略。**

### 错误示范
```yaml
description: |
  必须先执行以下步骤，再去查阅文档：
  1. 问用户期望的输出
  2. 识别核心约束
  ...
```

AI 的推理：
```
"我应该先问用户" → 
"但我觉得先了解 API 能力再问更好" → 
自己优化了流程 → 先读文档
```

### 正确做法
**使用禁止性语言，不给 AI 自由发挥的空间：**

```yaml
description: |
  🚫 禁止：识别到关键词时，禁止先读取文档/网页，禁止先搜索。
  
  ✅ 必须先做：直接回复用户，问以下问题（不要先读文档）：
  1. 「你期望的输出长什么样？」
  ...
```

### Skill vs Rule 选择指南

| 场景 | 选择 | 原因 |
|------|------|------|
| 必须严格遵守的规则 | **Rule** (alwaysApply) | 直接注入系统提示，强制执行 |
| 可选能力/工具 | **Skill** | 按需加载，节省 token |
| 必须执行但不想占 token | **Skill + 禁止性语言** | 在 description 中用强硬措辞 |

### Skill description 措辞原则

| 效果 | 措辞示例 |
|------|----------|
| ❌ 弱（会被忽略） | "建议先..."、"应该先..."、"最好先..." |
| ⚠️ 中（可能被忽略） | "必须先..."、"需要先..." |
| ✅ 强（会被遵守） | "🚫 禁止..."、"不允许..."、"禁止先...再..." |

### 经验如何才能被主动应用

1. **Skill 的 alwaysApply 不等于自动执行**
   - alwaysApply: true 只是让 skill 加载到上下文
   - AI 仍然需要"决定"是否读取和执行 SKILL.md

2. **把核心规则写在 description 中**
   - 不要依赖 AI 去读取 SKILL.md
   - description 匹配时，AI 能直接看到规则

3. **Rule 比 Skill 更可靠**
   - Rule 直接注入系统提示
   - 没有"AI 决定是否读取"这一步

### 反例
❌ 用"必须"、"应该"等建议性语言，期望 AI 严格遵守
❌ 把关键规则只写在 SKILL.md 中，description 只有简短描述
❌ 期望 alwaysApply: true 就能让规则自动执行

## file-ladder 路径冲突问题排查
<!-- 日期: 2026-01-23 -->

### 场景
使用 `file-ladder up` 命令时报错"所有服务器均无法连接"。

### 排查步骤
**第一步：查看 file-ladder 有几个路径**
```bash
where file-ladder
```

### 正确情况（只有一个路径）
```
C:\common_bin\file-ladder.exe
```
→ 路径正确，问题可能是网络或服务器问题

### 错误情况（有多个路径）
```
C:\Users\xxx\file-ladder.exe      ← 本地下载的（优先级高，但配置错误）
C:\common_bin\file-ladder.exe     ← 正确的公共版本
```
→ 本地版本会优先被使用，导致报错

### 解决方法
删除本地的 `file-ladder.exe`：
```bash
del C:\Users\xxx\file-ladder.exe
```
删除后再次运行即可正常使用。

用户经验分享 - 2026-01-23

## 多 Git 子仓库项目结构识别
<!-- 日期: 2026-01-22 -->

### 场景
用户要求拉取代码，但当前工作区显示 "Is directory a git repo: No"。

### 经验
**父目录不是 git 仓库 ≠ 没有 git 仓库，可能是多个独立子仓库的结构。**

### 识别方法
1. 先用 `ls` 查看目录结构
2. 进入各子目录执行 `git remote -v` 检查是否为独立仓库
3. 记录子目录与 git 地址的映射关系

### 正确操作流程
```bash
# 1. 不要在根目录执行 git 命令（会报错）
git pull  # ❌ fatal: not a git repository

# 2. 进入子目录操作
cd 子目录名
git status         # 检查状态
git pull origin master  # 拉取代码
```

### 拉取前必做检查
```bash
# 进入子目录后，先检查是否有未提交的修改
git status

# 如有修改，根据情况处理：
git stash           # 暂存修改
git checkout -- .   # 丢弃修改
git commit          # 提交修改
```

### 批量操作技巧
如果项目有多个子仓库需要同时更新，可以用循环：
```bash
for dir in 子仓库1 子仓库2 子仓库3; do
  echo "=== $dir ===" && cd "$dir" && git pull origin master && cd ..
done
```

### 反例
❌ 看到 "not a git repo" 就问用户要 git 地址，没有检查子目录
❌ 在根目录执行 `git init`，破坏了多仓库结构
❌ 没有先 `git status` 检查，直接 pull 导致冲突

### 正确做法
✅ 先 `ls` 查看子目录结构
✅ 逐个检查子目录是否有 `.git` 或执行 `git remote -v`
✅ 识别出多仓库结构后，分别进入操作
✅ 每次 pull 前先 `git status` 检查本地状态
